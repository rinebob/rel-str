## Goal

Move all indicator calculations out of the frontend and make the backend the single source of truth for ST indicator time series. The frontend will call a backend callable on demand and plot the returned series. Strategy signal generation will also move to the backend and remain separate from the indicator math.

We are deliberately **not** storing the full indicator series in Firestore. The docs are too large, they crash the Firebase console, and maintaining a separate computed dataset is a recurring burden.

## Why now

- The same indicator math (`ST-Trend-Bands`, `ST-Zone`, `ST-Trend-Strength`) is currently duplicated in `src/app/features/shared/components/flex-chart/indicators/` and `functions/src/indicators/`.
- The frontend recomputes these on every chart open, which is wasted work and a source of drift between chart visuals and backend signals.
- Strategy rules will be changing soon (removing HTF alignment, modifying zone rules, adding trend-strength and trigger-band strategies). We want the indicator math settled and shared before the strategy refactor begins.

## Decision log

### 1. Delivery pattern: backend callable on demand

The frontend will fetch indicator series via `rhAgentGetSymbolIndicatorSeries`, a callable that reads `rs-bars/{symbol}` and computes only the requested intervals, indicators, and strategies.

```
Frontend  ──onCall──►  rhAgentGetSymbolIndicatorSeries(symbol, intervals, indicators, strategies)
                       └── reads rs-bars/{symbol}
                       └── computes only requested indicators + signals
                       └── returns filtered payload
```

**Rationale:**
- Keeps `rs-bars/{symbol}` as the single source of truth for raw OHLCV bars.
- No Firestore document-size problems. No console crashes. No 13-decimal rounding hacks.
- No backfill, no worker indicator persistence, no duplicate dataset to maintain.
- The backend is the single source of truth for both indicator math and signal rules.
- The frontend requests exactly what it needs. If only one indicator is visible, only that indicator is computed and returned.
- Latency is acceptable during active trading hours because the function stays warm. We can add `minInstances: 1` later if cold starts become a problem.

### 2. Signal markers are bundled in the callable response

Signal markers are generated by the same backend function from the same indicator series. They are returned alongside the indicator series in the callable response, but they are **not** stored separately in Firestore in Phase 1.

**Rationale:**
- The chart needs both indicators and markers in one render pass.
- Strategy signal rules will change; keeping them in the callable lets the frontend stay dumb.
- The canonical signal list for the grouped review and signal list pages remains the existing `rh-agent-symbols/{symbol}/signal-history/{date}` and `run-ids/{runId}` docs.

### 3. Existing signal docs stay for lists and reviews

The callable response is a rendering payload only. The grouped review and signal list pages continue to read from the existing signal persistence layer.

### 4. Frontend caching with NgRx Signal Store

The frontend will cache callable responses in an NgRx Signal Store. The cache key is derived from the symbol, the active filter set, and a version property on the `rs-bars/{symbol}` doc. When the bars update, the version changes, and the cache naturally invalidates.

```
rs-bars/{symbol}  ──►  version field
                          │
                          ▼
Frontend cache key = symbol + filters + rsBarsVersion
                          │
                          ▼
                  rhAgentGetSymbolIndicatorSeries
```

**Rationale:**
- Recomputing indicators on every page navigation is wasteful; price data changes only ~4 times per day.
- The Signal Store provides a reactive, shared cache that multiple components can read without duplicate calls.
- Cache invalidation is automatic because the source-of-truth version is part of the key.
- No dual-timestamp logic; a single `version` field is enough to bust the cache.

### 5. Add a `version` field to `rs-bars/{symbol}` docs

The `rs-bars/{symbol}` document will include a `version` field that is updated every time the nightly sync or an intraday PDR run writes new data. The frontend reads this field when it loads bars and uses it to key the indicator cache.

**Rationale:**
- A dedicated version field is explicit and reliable. Timestamps can be ambiguous across time zones or partial writes.
- The frontend already reads `rs-bars/{symbol}`; adding one field has no extra cost.
- The worker that writes `rs-bars` is the same worker that writes intraday snapshots, so it can bump the version atomically.

## Phased approach

### Phase 1 — Indicators via callable

**Goal:** Backend owns all indicator time series; frontend fetches them via callable and plots them without recomputation.

**Backend:**
- Keep the shared pure computation module (`rh-agent-indicator-computation`) that calls the existing indicator math and packages the outputs.
- Expose and finalize `rhAgentGetSymbolIndicatorSeries` callable. It accepts `intervals`, `indicators`, and `strategies` filters, reads `rs-bars/{symbol}`, computes only the requested data, and returns the filtered `SymbolIndicatorSeriesResponse`.
- Add a `version` field to `rs-bars/{symbol}` docs and bump it whenever the nightly sync or an intraday PDR run writes data.
- Do **not** write `st-indicators` docs from the worker or a backfill script.

**Frontend:**
- Create an NgRx Signal Store (`IndicatorSeriesStore`) that holds cached callable responses keyed by `[symbol, filters, rsBarsVersion]`.
- `RhAgentChartService` reads `rs-bars/{symbol}` to get the bars and the `version`, then calls the store's `loadIfNeeded` action with the active filters.
- The store issues the callable only when no cached entry exists for the key, or when the requested filters are not covered by the cache.
- Update `signal-detail.component.ts` to read indicators from the store instead of computing them inline.
- Update the flex chart indicators to use the store data directly.
- Deprecate or remove the inline frontend calculators.

**Signals:**
- The callable returns signal markers computed by the current backend signal rules.
- The canonical signal list for grouped review remains unchanged.

### Phase 2 — Trigger bands

**Goal:** Add `ST-Trigger-Band` to the backend indicator library.

**Backend:**
- Port the trigger-band math to `functions/src/indicators/`.
- Include trigger-band series in the `SymbolIndicatorSeriesResponse` returned by the callable.

**Frontend:**
- Remove the frontend trigger-band calculator.
- Plot from the callable response.

### Phase 3 — Strategy refactor

**Goal:** Update signal rules and return chart markers from the backend.

**Backend:**
- Remove HTF alignment from zone-based signals.
- Modify zone V1/V2 rules.
- Add trend-strength and trigger-band strategies.
- Strategy worker writes `rh-agent-symbols/{symbol}/signal-history/{date}` using the same signal detection logic that produces the chart markers.
- The callable returns the updated chart markers alongside the indicator series.

**Signal consistency principle:**
The signal-history docs and the chart marker response must be produced from the same signal detection pass. The worker's strategy adapter and the callable both call the same `detectLastBarSignals` / `detectTrendStrengthSignals` functions. The worker writes the signal-history docs; the callable recomputes the markers on demand. Because the math is deterministic from the same `rs-bars` input, the two outputs match. If the rules change, they change in one place.

**Frontend:**
- Plot signal markers from the callable response.
- Remove the remaining frontend signal-detection logic.

## Callable request/response shape

The `rhAgentGetSymbolIndicatorSeries` callable accepts a filter and returns only the requested data.

### Request

```typescript
export enum ChartInterval {
  DAILY = 'daily',
  WEEKLY = 'weekly',
  MONTHLY = 'monthly',
}

export enum IndicatorFamily {
  ZONE_V1 = 'zoneV1',
  ZONE_V2 = 'zoneV2',
  TREND_STRENGTH = 'trendStrength',
  TREND_BANDS = 'trendBands',
  TRIGGER_BANDS = 'triggerBands',
}

export enum StrategyFamily {
  ZONE_V1 = 'zoneV1',
  ZONE_V2 = 'zoneV2',
  TREND_STRENGTH = 'trendStrength',
  TRIGGER_BANDS = 'triggerBands',
}

interface GetIndicatorSeriesRequest {
  symbol: string;
  marketDate?: string;
  intervals?: ChartInterval[];
  indicators?: IndicatorFamily[];
  strategies?: StrategyFamily[];
}
```

Omitted filters default to all values. Invalid values are ignored or rejected with `invalid-argument`.

### Response

```typescript
interface SymbolIndicatorSeriesResponse {
  symbol: string;
  marketDate: string;
  computedAt: string;
  intervals: {
    daily?: IntervalData;
    weekly?: IntervalData;
    monthly?: IntervalData;
  };
}

interface IntervalData {
  indicators: {
    zoneV1?: ZonePoint[];
    zoneV2?: ZonePoint[];
    trendStrength?: TrendStrengthPoint[];
    trendBands?: TrendBandsPoint[];
    triggerBands?: TriggerBandsPoint[];
  };
  signals: {
    zoneV1?: SignalMarker[];
    zoneV2?: SignalMarker[];
    trendStrength?: SignalMarker[];
    triggerBands?: SignalMarker[];
  };
}

interface ZonePoint {
  d: string;
  zoneV1: number | null;
  zoneV2: number | null;
  htfZoneV2: number | null;
}

interface TrendStrengthPoint {
  d: string;
  diPlus: number | null;
  diMinus: number | null;
  diHist: number | null;
  adx: number | null;
}

interface TrendBandsPoint {
  d: string;
  bands: BandPoint[]; // Array of 4 bands, indexed by bandIndex (1..4)
}

interface BandPoint {
  bandIndex: number;
  bullColor: string;
  bearColor: string;
  open: number | null;
  high: number | null;
  low: number | null;
  close: number | null;
  mid: number | null;
  up: boolean | null;
}

interface TriggerBandsPoint {
  d: string;
  // Trigger band fields TBD in Phase 2
}

interface SignalMarker {
  d: string;
  index: number;
  direction: 'long' | 'short';
  signalType: string;
  reason: string;
}
```

**Separation of concerns:**
- `computeIndicatorSeries` stays pure. It produces the indicator time series.
- `generateSymbolSignals` consumes the indicator series and bars, runs the strategy rules, and produces signal markers.
- The callable filters both and returns only what was requested. Nothing is stored in Firestore except the source `rs-bars/{symbol}` doc.

## Intraday indicators

The callable recomputes the full indicator series on every call from the current `rs-bars/{symbol}` doc. If the nightly sync has already run today, the last bar is the completed EOD bar. If the RH Agent worker has run an intraday PDR, the last bar is the partial intraday bar. The frontend always receives the latest available view without needing to reason about dual timestamps.

## Frontend consumption

1. `RhAgentChartService.loadBars$(symbol)` reads `rs-bars/{symbol}` and builds the D/W/M `ChartDataset` objects. It also extracts the `version` field.
2. `IndicatorSeriesStore.loadIfNeeded(symbol, version, intervals, indicators, strategies)` checks the cache. If the key is missing, it calls `rhAgentGetSymbolIndicatorSeries` and stores the result.
3. `signal-detail.component.ts` reads from the store and passes the pre-computed indicator series into the `IndicatorConfig` objects for `FlexChartComponent`.
4. `FlexChartComponent` already uses `config.data` if provided; no change needed to the core chart renderer.
5. The store exposes a computed value for the combined chart data so the component does not recompute on every signal change.

## Caching detail

The NgRx Signal Store holds a map of cached responses.

```typescript
interface IndicatorSeriesCacheEntry {
  key: string;
  symbol: string;
  version: string;
  intervals: ChartInterval[];
  indicators: IndicatorFamily[];
  strategies: StrategyFamily[];
  response: SymbolIndicatorSeriesResponse;
  loadedAt: string;
}

interface IndicatorSeriesStoreState {
  cache: IndicatorSeriesCacheEntry[];
  loading: boolean;
  error: string | null;
}

const cacheKey = (symbol: string, version: string, intervals: string[], indicators: string[], strategies: string[]) =>
  [symbol, version, intervals.sort().join(','), indicators.sort().join(','), strategies.sort().join(',')].join('|');
```

**Cache behavior:**
- `loadIfNeeded` builds the key and checks for an exact match.
- If found, it returns the cached response.
- If not found, it calls the callable, stores the response, and returns it.
- The store never re-fetches for the same key. The `version` field ensures the cache invalidates automatically when the bars change.
- When the cache grows too large, entries can be evicted by a simple LRU policy or by limiting the number of cached symbols.

## Open questions

1. Do we keep the frontend calculators as a fallback for offline development, or delete them immediately? **Decision:** Keep the legacy calculator files in place, but route production chart rendering through the callable. Do not use the legacy code as a fallback in the production path, because it can hide bugs in the new data flow. Delete the legacy calculators in a later cleanup pass.
2. Should we add `minInstances: 1` to the callable from the start? **Decision:** No. During trading hours the function will stay warm from regular use. If cold starts become a user-visible problem, add it later.

## Future work

- Phase 2: Trigger bands added to the callable response.
- Phase 3: Strategy rule refactor; signal markers continue to be returned by the callable.
- If the callable payload becomes too large or latency becomes unacceptable, consider year-sharded `st-indicators` docs or Cloud Storage JSON as the next step.
