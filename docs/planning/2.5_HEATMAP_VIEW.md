# 2.5 Heatmap View (vNext)

## 1. Goals and Scope

The existing `dashboardV2` heatmap implementation is brittle, difficult to reason about, and tightly coupled to list editing and legacy data flows. This document defines the **vNext Heatmap View** architecture:

- A new, RxJS-first heatmap implementation.
- New standalone Angular component(s).
- A dedicated Signal Store for heatmap state.
- A thin data service responsible for talking to Firestore/Cloud Functions.

The vNext heatmap is **independent of `dashboardV2`**, which will be deprecated and left unchanged.

Design priorities:

- **Single source of truth** for "what the heatmap should show now".
- **Explicit state machine** for loading, streaming, and error states.
- **Efficient reads** from Firestore/Functions for 30–50 symbols per list.
- **Correct handling of pre-close (intraday) vs post-close (canonical) RS values.**
- **RxJS Observables as the canonical async primitive** throughout the store and services.

## 2. Core Types

### 2.1 HeatmapQuery

`HeatmapQuery` is the canonical input that defines what data the heatmap should display.

```ts
interface HeatmapQuery {
  listId: string;                 // Selected list identity
  baseline: string;               // Baseline symbol (e.g. "SPY", "IWM")
  symbols: string[];              // Ordered target symbols from the list
  interval: 'DAILY' | 'WEEKLY' | 'MONTHLY';
  phaseMode: 'canonicalOnly'      // Show canonical post-close values only
            | 'preAndPost'        // Today shows pre-close; history is post-close
            | 'intradayZoom';     // Future: intraday-only view for current day
  rangeDays?: number;             // Optional window length (e.g. 20 days)
}
```

- The **store owns the current `HeatmapQuery`** as a signal.
- All data loading is a pure function of this query.

### 2.2 HeatmapSlice (Data Contract)

`HeatmapSlice` is the normalized data representation the heatmap store expects from the data service. It is independent of Firestore's internal document layout (`pairs-data/*` etc.).

```ts
interface HeatmapColumnMeta {
  date: string;                   // e.g. "2026-01-05" (ISO day key)
  phase: 'pre' | 'post';          // Phase represented in this column
  isToday: boolean;               // Whether this column corresponds to "today"
  lastUpdateTime?: number;        // Epoch ms of last update for this column (optional)
  isPreCloseStream?: boolean;     // True if this column is updated multiple times intraday
}

interface HeatmapRowMeta {
  pairId: string;                 // Backend pair key (e.g. SPY-AAPL)
  symbol: string;                 // Target symbol (e.g. "AAPL")
  baseline: string;               // Baseline symbol (e.g. "SPY")
}

interface HeatmapSlice {
  query: HeatmapQuery;            // The query this slice corresponds to
  rows: HeatmapRowMeta[];         // One per baseline/target pair
  columns: HeatmapColumnMeta[];   // One per day (or intraday bucket in zoom mode)
  // rsValues[rowIndex][colIndex] = RS value or null
  rsValues: (number | null)[][];
  meta: {
    isComplete: boolean;          // True when we have the full requested range
    missingDates: string[];       // Dates we expect but have no data for
  };
}
```

- The **data service** is responsible for mapping from Firestore/Functions responses
  (`pairs-data/.../archive*`, etc.) into this structure.
- The heatmap store does **not** know or care about document shapes.

### 2.3 HeatmapViewModel (UI Contract)

`HeatmapViewModel` is the shape consumed by the Angular component. It encodes lifecycle and sorting state as well as display-ready metadata.

```ts
export enum HeatmapState {
  IDLE = 'idle',                  // No query yet
  LOADING_HISTORY = 'loading-history', // Fetching historical slice
  LOADING_TODAY = 'loading-today',  // Backfilling/streaming today's column
  READY = 'ready',                // Fully usable
  ERROR = 'error',                // Failed; error message present
}

interface HeatmapSortSpec {
  columnIndex: number | null;     // Null = default sort (e.g. by symbol)
  direction: 'asc' | 'desc';
}

interface HeatmapStatus {
  state: HeatmapState;
  errorMessage?: string;
}

interface HeatmapHeaderCellVM {
  label: string;                  // e.g. "Dec 20" or "Jan 05"
  subLabel?: string;              // e.g. weekday, phase indicator
  tooltip?: string;               // e.g. full date + last update time
  isToday: boolean;
  isLastColumn: boolean;
}

interface HeatmapCellVM {
  value: number | null;
  color: string;                  // CSS color (derived from value)
  tooltip?: string;               // e.g. RS value + date + phase
}

interface HeatmapRowVM {
  symbol: string;
  baseline: string;
  cells: HeatmapCellVM[];
}

interface HeatmapViewModel {
  query: HeatmapQuery | null;
  status: HeatmapStatus;
  headerCells: HeatmapHeaderCellVM[];
  rows: HeatmapRowVM[];
  sort: HeatmapSortSpec;
}
```

- The **store** produces `HeatmapViewModel` as a derived signal.
- The **component** binds directly to this view model and never interprets raw data.

## 3. Directional Contracts

### 3.1 Stock-List v2 → Heatmap Store

Stock-list v2 is responsible for **list selection and editing**, not heatmap data.

**Contract:**

- Stock-list v2 exposes a reactive `SelectedList` structure:

  ```ts
  interface SelectedList {
    id: string;
    baseline: string;
    symbols: string[]; // ordered
    name: string;
  }
  ```

- The heatmap store derives `HeatmapQuery` from this plus local UI preferences:

  - `listId = selectedList.id`
  - `baseline = selectedList.baseline`
  - `symbols = selectedList.symbols`
  - `interval`, `phaseMode`, `rangeDays` come from heatmap-local settings or user controls.

- Stock-list v2 does **not**:

  - Provide RS values or ranks to the heatmap.
  - Orchestrate heatmap data loading.
  - Perform its own calls to `pairs-data`.

### 3.2 Firebase → Heatmap Store

The backend currently stores RS data under `pairs-data/{pairId}/archive*` documents with `rsRaw` and related fields.

**Contract (vNext):**

- The heatmap data **service** is the only frontend layer that:
  - Knows about `pairs-data` paths.
  - Calls Firestore/Cloud Functions to retrieve RS histories.

- The service exposes a small, well-defined observable API:

  ```ts
  interface HeatmapDataService {
    // Historical + current-day slice for standard heatmap modes.
    getHeatmapSlice$(query: HeatmapQuery): Observable<HeatmapSlice>;

    // Future: intraday zoom mode where columns are intraday buckets
    // instead of days. Not required for initial vNext implementation.
    getIntradaySlice$(query: HeatmapQuery): Observable<HeatmapSlice>;
  }
  ```

- Internally the service may:
  - Use a callable function to fetch an aggregated slice.
  - Or perform batched Firestore reads and normalize them.
  - Maintain a small in-memory cache keyed by `{ listId, baseline, interval, rangeDays }`.

- Pre-close (intraday) updates for the **last column** are surfaced as **small deltas**, not full refetches:
  - Either via Firestore listeners on a compact `latest` document, or
  - Via a streaming callable / polling wrapper that only touches the current day.

### 3.3 Heatmap UI → Heatmap Store

The new heatmap component is a **pure consumer of `HeatmapViewModel` and producer of user intent**.

**UI → Store (intents):**

- `setInterval(interval: 'DAILY' | 'WEEKLY' | 'MONTHLY')`
- `setPhaseMode(mode: HeatmapQuery['phaseMode'])`
- `setSort(sort: HeatmapSortSpec)`

**Store → UI (state):**

- A single `HeatmapViewModel` signal, e.g. `vm = heatmapStore.vm()`.
- UI binds to:
  - `vm.status` to show loading/error/ready states.
  - `vm.headerCells` for column headers (including last update time for the last column).
  - `vm.rows` for the table body.
  - `vm.sort` for sort UI state.

The component does **not**:

- Make direct Firestore or Cloud Function calls.
- Manage manual staleness guards.
- Re-interpret raw RS values.

## 4. State Machine & RxJS Flows

### 4.1 High-Level State Machine

For a given `HeatmapQuery`, the store follows an explicit state machine:

1. **idle** → no query yet.
2. **loadingHistory** → fetch historical slice for the requested range.
3. **loadingToday** → backfill or stream today's last column (pre/post).
4. **ready** → both history and today's column are in place.
5. **error** → any unrecoverable error during loading.

Transitions are driven by:

- Changes to `HeatmapQuery` (new list, baseline, interval, phaseMode).
- Notifications from the data service (history loaded, today updated, errors).

### 4.2 RxJS Principles

- **Observable-first:**
  - Data service exposes observables only; no new promise-based APIs.
  - Store uses RxJS operators (`switchMap`, `shareReplay`, `catchError`, `map`) to implement transitions.

- **Cancellation:**
  - Query changes are handled via `switchMap` so obsolete loads are automatically cancelled.

- **Performance:**
  - Use caching in the service for repeated queries (e.g. switching back to a recent list).
  - Batch RS reads to minimize Firestore/Functions round trips for 30–50 symbols.

## 5. Future Enhancements

### 5.1 Streaming Pre-Close Updates

- Last column in the heatmap will represent the **current day**.
- As pre-close RS updates arrive from SavantAPI via the backend, the data service will:
  - Update the latest RS value per pair for today.
  - Annotate `HeatmapColumnMeta.lastUpdateTime`.
  - Mark `isPreCloseStream = true`.
- The store will surface this via `HeatmapViewModel.headerCells` so the UI can show the update time in the last column header.

### 5.2 Intraday Zoom View

A future view will allow users to "zoom in" on the current day:

- Each pre-close update becomes its own **intraday cell**.
- Columns represent intraday time buckets rather than days.
- The same contracts apply:
  - `phaseMode = 'intradayZoom'` on `HeatmapQuery`.
  - `HeatmapSlice.columns` and `HeatmapViewModel.headerCells` are adapted to intraday keys.

This design ensures that intraday behavior is a **mode of the same state machine**, not a separate ad-hoc implementation.

### 5.3 RSMA-Based Scoring and Sorting (Planned)

- **Definition:** RSMA is an EMA-based moving average over RS values per pair:
  - RSMA window options: 5, 10, 30 RS periods.
  - RSMA is computed independently for each interval (DAILY, WEEKLY, MONTHLY) from the corresponding RS series.
  - For a given interval, `RSMA_L = EMA_L(RS_t)` over the last `L` RS samples (where each RS sample is already based on a 5-period RS window).

- **Usage in heatmap:**
  - Sorting: when the user selects an RSMA window (5/10/30) and clicks a sortable RS-oriented column, the store will rank rows by the selected RSMA value for that column/interval instead of the single-period RS value.
  - Coloring: v1 keeps cell color based on the underlying RS value; RSMA only affects row ordering.

- **Implementation notes:**
  - RSMA is initially computed **in the dashboard-v3 Signal Store** from the `HeatmapSlice.rsValues` array; no new Firestore fields are required for v1.
  - RSMA must support all three intervals in `HeatmapQuery.interval` (`DAILY`, `WEEKLY`, `MONTHLY`). The scoring logic itself is interval-agnostic; it operates over the RS series supplied by the data service.
  - EMA must be implemented in a reusable TS utility to ensure consistent scoring across consumers.

- **Future work (not in v1):**
  - Add a UI toggle to color the heatmap cells by RSMA instead of RS for better visualization of smoothed strength.
  - Persist per-user RSMA preferences (window, coloring mode) using the existing state persistence strategy so the app restores the last-used scoring configuration on reload.

## 6. Implementation Phases

1. **Define Heatmap Store (Signal Store + RxJS)**
   - Implement `HeatmapQuery` as store input.
   - Implement RxJS pipeline from `HeatmapQuery` to `HeatmapSlice` to `HeatmapViewModel`.

2. **Implement Data Service**
   - Wrap Firestore/Functions access.
   - Normalize backend data into `HeatmapSlice`.
   - Add basic caching and error handling.

3. **Implement New Heatmap Component**
   - Standalone Angular component using Signals and new control flow syntax.
   - Binds only to `HeatmapViewModel` and calls store intent methods.

4. **Integrate with Stock-List v2**
   - Wire `SelectedList` into the heatmap store as the source for `listId`, `baseline`, and `symbols`.

5. **Deprecate `dashboardV2` Heatmap**
   - Keep the legacy view read-only and mark it as deprecated in docs and UI.
   - Gradually migrate users and features to the vNext heatmap.
