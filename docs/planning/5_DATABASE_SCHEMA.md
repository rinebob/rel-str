# Database Schema and Management - Relative Strength Heatmap (MVP) - Combined (Revised)

## 1. Introduction

This document outlines the planned database schema in Firebase Cloud Firestore and related management considerations for the Minimum Viable Product (MVP) of the Relative Strength Heatmap (RSH) application. The schema is designed to support efficient storage and retrieval of user data, personalized stock lists, and historical and daily stock data required for Relative Strength calculations and frontend visualization, leveraging Firestore's scalability and integration with other Firebase/GCP services. It specifically accommodates storing both pre-close and post-close Relative Strength values for each trading day.

## 2. Database Choice: Firebase Cloud Firestore

* **Choice:** Firebase Cloud Firestore
* **Type:** NoSQL Cloud Database
* **Description:** Firebase Cloud Firestore is selected as the primary database. It is a flexible, scalable NoSQL cloud database that provides real-time synchronization capabilities (beneficial for future features) and is designed for tight integration with other Firebase services like Authentication and Cloud Functions. It will store user profiles, user-defined stock lists, application settings, and the core calculated Relative Strength (RS) and historical OHLCV data.

## 3. Collections and Documents

Firestore data will be organized into Collections, containing Documents, which can in turn contain subcollections. The primary collections and document structures for the MVP are:

* **`users` Collection:**
    * Stores documents representing each user account.
    * Document ID: The Firebase Authentication User UID (`auth.uid`).
    * Fields:
        * `email` (string, indexed for queries if needed)
        * `displayName` (string, optional)
        * `createdAt` (timestamp - Creation date/time)
        * `subscriptionStatus` (string: e.g., 'free', 'paid', 'admin')
        * `subscriptionDetails` (map, optional - used to store payment gateway subscription IDs, renewal dates, etc.)
        * `preferences` (map, optional - user-specific settings like defaultBaseline ticker, theme choice, etc.)
        * `selectedTickers` (array of strings - the list of ticker symbols the user tracks for their heatmap)
    * **`paymentHistory` Subcollection (under each user document):**
        * Stores documents representing individual payment transactions or subscription events for a specific user.
        * Document ID: Auto-generated by Firestore or potentially the payment gateway transaction/event ID.
        * Fields:
            * `amount` (number)
            * `currency` (string)
            * `date` (timestamp - Date/time of the transaction/event)
            * `status` (string, e.g., 'completed', 'failed', 'subscription.created', 'invoice.paid')
            * `description` (string, e.g., 'Monthly Subscription Payment')
            * `paymentGatewayDetails` (map, optional - store relevant IDs and details from Stripe/PayPal webhook payloads)

* **`symbols` Collection:**
    * Stores documents representing each security/ticker symbol for which RS and historical data is tracked.
    * Document ID: The Ticker Symbol (string, e.g., "AAPL", "MSFT", "SPY").
    * Fields:
        * `companyName` (string, optional but helpful for display/identification)
        * `industry` (string, optional - potential future filtering/grouping)
        * `latestData` (map - Stores the most recent daily summary data, including both pre- and post-close RS values and timestamps, optimized for heatmap display efficiency)
            * `date` (timestamp - The market close date the data corresponds to)
            * `open` (number)
            * `high` (number)
            * `low` (number)
            * `close` (number)
            * `volume` (number)
            * `preCloseRSValue` (number - The calculated RS value using data available *before* market close)
            * `preCloseTimestamp` (timestamp - Indicates when the pre-close value was calculated/updated)
            * `postCloseRSValue` (number - The calculated RS value using market close data)
            * `postCloseTimestamp` (timestamp - Indicates when the post-close value was calculated/updated)
        * *(Note: The `latestData` map is optimized for quickly reading the most current data across multiple symbols for the heatmap. The historical data for a symbol over time, including the pre/post RS values for each historical day, is stored in the subcollection.)*
    * **`historicalData` Subcollection (under each symbol document):**
        * Stores documents representing the historical daily OHLCV data and the corresponding calculated pre- and post-close RS values for that specific day.
        * Document ID: Date (string "YYYY-MM-DD" or Timestamp - using a consistent format, often "YYYY-MM-DD" string simplifies querying specific dates or ranges by string comparison/ordering).
        * Fields:
            * `date` (timestamp - Redundant with ID if using timestamp, but useful if ID is string. Represents the market close date.)
            * `open` (number)
            * `high` (number)
            * `low` (number)
            * `close` (number)
            * `volume` (number)
            * `preCloseRSValue` (number - The calculated RS value for this day using pre-close data)
            * `preCloseTimestamp` (timestamp - Indicates when the pre-close value for this day was calculated)
            * `postCloseRSValue` (number - The calculated RS value for this day using market close data)
            * `postCloseTimestamp` (timestamp - Indicates when the post-close value for this day was calculated)

* **`appConfig` Collection:**
    * Stores application-wide configuration documents.
    * Document ID: A fixed, predefined ID (e.g., "settings", "config").
    * Fields:
        * `scheduledFetchTime` (string or timestamp - The target time for the daily data fetch process, e.g., '15:00 America/New_York')
        * `nextScheduledFetch` (timestamp - The actual upcoming scheduled run time for the data fetch/calc process)
        * `rsLookbackDays` (number - The default or configurable number of days for the RS calculation lookback period, e.g., 252 for approximate 1-year)
        * `masterSymbolList` (array of strings - The definitive list of ~500 ticker symbols the backend attempts to fetch data for daily)
        * `seedSymbolList` (array of strings - A smaller default list of tickers provided to new users initially, e.g., ~10 diverse symbols)
        * `rsGradientColors` (map or array - Definition of the color gradient scale used for heatmap visualization based on RS values)
        * ... other global configuration settings ...

## 4. Indexing

Firestore requires indexes for most queries that involve filtering or ordering data. Indexes will be defined to support the anticipated frontend and backend query patterns.

* Retrieving a specific user document by their Firebase Auth UID (document ID lookup is indexed automatically).
* Retrieving a user's payment history by date within the `paymentHistory` subcollection (requires index on `date` field).
* Retrieving a specific symbol document by its ticker symbol (document ID lookup is indexed automatically).
* Retrieving historical data for a specific symbol within a date range from the `historicalData` subcollection, ordered by date (requires index on `date` field in the subcollection).
* Querying the top-level `symbols` collection based on fields within the `latestData` map, such as filtering by `latestData.postCloseRSValue` or `latestData.calcTimestamp` (e.g., find all symbols with latest post-close RS > 80, or find symbols with stale data). This is feasible and efficient with proper indexing defined on the specific subfields (`latestData.postCloseRSValue`, `latestData.calcTimestamp`, etc.). Composite indexes might be required for queries combining multiple fields from `latestData`.
* Filtering the `users` collection by `subscriptionStatus`.

## 5. Data Loading & Access Patterns

Understanding the primary data access patterns helps optimize the schema and queries:

* **Heatmap Display:**
    1.  Fetch the `selectedTickers` array from the current user's document.
    2.  Perform multiple parallel reads to fetch the `latestData` map from the corresponding documents in the top-level `symbols` collection for each ticker in the `selectedTickers` array. The frontend will then use the appropriate RS value (`preCloseRSValue` or `postCloseRSValue`) and timestamp (`preCloseTimestamp` or `postCloseTimestamp`) from the `latestData` map based on the time of day or data availability.
* **Chart Display:**
    1.  Fetch the specific symbol document from the `symbols` collection to get `latestData` and other symbol info.
    2.  Query the `historicalData` subcollection for that symbol, filtering by a date range and ordering by date. The frontend chart component will receive documents containing both `preCloseRSValue` and `postCloseRSValue` for each historical day and can render them as needed (e.g., plotting both lines, plotting only post-close, coloring bars based on post-close).
* **Scheduled Fetch/Calc (Backend):**
    1.  Read the `masterSymbolList` and configuration (`rsLookbackDays`, etc.) from the `appConfig` collection.
    2.  Read necessary historical OHLCV data from `historicalData` subcollections across various symbols for calculations (lookback period).
    3.  Write/update the `latestData` map in documents in the `symbols` collection with the most recent OHLCV, pre-close RS, post-close RS, and timestamps.
    4.  Write new daily documents to the `historicalData` subcollections, including the day's OHLCV and calculated pre-close/post-close RS values and timestamps for that specific day.
* **User List Management:** Read/write the `selectedTickers` array in the user's document.

## 6. Security Rules

Firestore Security Rules are critical for enforcing data access control and preventing unauthorized reads or writes from the client-side. Rules will be strictly defined to ensure:

* Users can only read and write their *own* document in the `users` collection (`/users/{userId}` where `userId` matches the authenticated user's UID).
* Users can only read and write documents within their *own* `paymentHistory` subcollection (`/users/{userId}/paymentHistory/{paymentId}`).
* Authenticated users can *read* documents in the top-level `symbols` collection (`/symbols/{symbol}`) and documents within their `historicalData` subcollections (`/symbols/{symbol}/historicalData/{date}`). However, *writes* to the `symbols` collection and its `historicalData` subcollections will be denied from the client-side. Writes will only be permitted from authenticated Firebase Cloud Functions using the Admin SDK.
* Authenticated users will be allowed to *read* the `appConfig` collection (`/appConfig/{configId}`) to retrieve necessary client-side configuration like the next fetch time or color gradients. Writes to `appConfig` will be restricted to administrators or specific backend processes.

## 7. Migrations

* **Strategy (MVP):** Manual updates and simple scripts.
* **Description:** For the MVP phase, database schema changes (adding/removing fields, simple restructuring) will primarily be handled manually via custom one-off scripts written in Node.js (using the Firebase Admin SDK) or direct updates as needed. A formal, versioned database migration strategy or automated tool is not planned for the initial MVP release but will be a key consideration for future development as the schema complexity and data volume grow.

## 8. Backups

* **Requirement:** Automated database backups are required for disaster recovery and data protection.
* **Strategy:** Utilize Firebase Firestore's managed export and backup solutions provided via Google Cloud.
* **Details:** Configure scheduled daily exports of the entire Firestore database to a Google Cloud Storage bucket. This ensures point-in-time recovery capability and provides a safeguard against accidental data loss or corruption, especially for the valuable historical `symbols` and `historicalData`. Specific backup frequency (e.g., daily) and retention policies (e.g., keep last 7 daily backups) will be determined based on cost implications and required Recovery Point Objectives (RPO).
