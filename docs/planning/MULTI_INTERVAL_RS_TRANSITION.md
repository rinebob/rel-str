# Multi-Interval RS Transition Plan (Daily / Weekly / Monthly)

## 1. Purpose

This document describes how we will integrate **weekly** and **monthly** RS data into the existing app without breaking current daily-only behavior. It is a **transition plan** for both backend and frontend:

- Preserve the current **daily RS pipeline** and UI.
- Add **weekly/monthly RS** using the same pair-centric schema (`pairs-data/{PAIR}`) and writer infrastructure.
- Introduce **Signals Activity** (`signals-activity`) to surface real-time preview vs final vs whipsaw events across all intervals.
- Prepare for code + doc updates in a controlled sequence.

Implementation and doc rewrites will happen in later steps. This file is the single source of truth for the transition.

### 1.1 Implementation Status (Canonical Engine)

Since this plan was drafted, the core backend engine for multi-interval RS has been implemented:

- **Canonical multi-interval engine** — `functions/src/webhooks/rs-canonical-engine.ts`:
  - Loads archive RS samples from `archive-YYYY`, `archive-weekly-YYYY`, and `archive-monthly-YYYY`.
  - Uses `rs-signals-engine.detectRsEvents` per interval (DAILY/WEEKLY/MONTHLY) to derive OPEN/CLOSE events.
  - Maps these to `RsWriteEvent[]` (with `rsRawYesterday/rsRawToday`, `rsNormYesterday/rsNormToday`, `price`, `positionId`, `direction`, `interval`).
  - Calls `rs-events-consumer.applyRsEventsForPair(writes)` as the single writer for:
    - Per-pair canonical signals under `pairs-data/{PAIR}/signals/{YYYY}/opens|closes/{signalId}`.
    - Root positions and timelines under `positions/{open|YYYY-closed}/items/{positionId}`.
- **Signals Activity helper** — `functions/src/webhooks/activity-from-writes.ts`:
  - `generateActivityFromWrites` groups canonical writes by `(interval, positionId)`.
  - Derives `openDay`/`closeDay` per position and walks archive RS samples in that interval.
  - Emits `ActivityEvent` rows (OPEN/HOLD/CLOSE) for DAILY/WEEKLY/MONTHLY, written as PREVIEW entries under per-pair and root `signals-activity` mirrors.
- **Shared across backfill and realtime POST**:
  - Historical backfill and realtime POST both call `runCanonicalRsEngineForPair` and `applyRsEventsForPair`.
  - Both derive multi-interval Signals Activity via `generateActivityFromWrites`.

The remaining sections in this document describe the broader transition (FE integration, cleanup) and should be read in light of this now-implemented backend core.

## 2. Current State (Daily-Only Summary)

### 2.1 Backend

- **Pairs**:
  - `pair-registry/{BASE}-{SYMBOL}` controls which pairs the scheduler computes.
- **Daily RS series**:
  - `pairs-data/{PAIR}` with:
    - `meta { baseline, symbol }`.
    - `lastUpdatedAt`.
    - `latest` (effectively daily-only today; PRE/POST semantics).
  - `pairs-data/{PAIR}/archive-YYYY/{YYMMDD}` per-day docs with `pre` and `post`.
- **Signals**:
  - Canonical signals under:
    - `pairs-data/{PAIR}/signals/{YYYY}/opens/{signalId}`.
    - `pairs-data/{PAIR}/signals/{YYYY}/closes/{signalId}`.
  - Generated by `rs-signals-engine.detectRsEvents` + `rs-events-consumer.applyRsEventsForPair`.
- **Signals mirrors** (legacy name):
  - `pairs-data/{PAIR}/signals-daily/{YYYY}/days/{YYYY-MM-DD}`.
  - `signals-daily/{YYYY}/days/{YYYY-MM-DD}`.
- **Positions**:
  - `positions/open/items/{positionId}`.
  - `positions/{YYYY}-closed/items/{positionId}`.

Today, everything is effectively **DAILY-only**, and the FE assumes:

- One RS interval.
- One signal cadence (end-of-day).
- `signals-daily` is a daily-only mirror.


### 2.2 Frontend

- Dashboard / Heatmap reads:
  - `pairs-data/{PAIR}.latest` for daily RS.
- Chart view reads:
  - Daily RS series from `pairs-data/{PAIR}` + archives.
- Signal/position views:
  - Use canonical daily signals and positions only.

## 3. Target State (Multi-Interval: D / W / M)

The target model adds **Weekly** and **Monthly** RS while keeping a single, pair-centric schema.

### 3.1 RS Series Per Interval

For each pair `{PAIR}`:

- **Daily** (existing, clarified):
  - `pairs-data/{PAIR}`:
    - `latestDaily` (PRE/POST daily mirror).
  - `pairs-data/{PAIR}/archive-YYYY/{YYMMDD}`:
    - `pre` and `post` daily snapshots with change vs prior POST.

- **Weekly** (new):
  - `pairs-data/{PAIR}`:
    - `latestWeekly` (current weekly snapshot, intraperiod or final).
  - `pairs-data/{PAIR}/archive-weekly-YYYY/{YYMMDD}`:
    - Same `pre`/`post` shape as daily, but computed from **weekly bars**.
    - `isIntervalClose: boolean` to mark final weekly bars.

- **Monthly** (new):
  - `pairs-data/{PAIR}`:
    - `latestMonthly` (current monthly snapshot, intraperiod or final).
  - `pairs-data/{PAIR}/archive-monthly-YYYY/{YYMMDD}`:
    - Same `pre`/`post` shape, computed from **monthly bars**.
    - `isIntervalClose: boolean` to mark final monthly bars.

**Key rules**:

- All three intervals (D/W/M) are updated on **every backend run** using the latest AV bars.
- For Weekly/Monthly, we treat intraperiod bars as **previews**; `isIntervalClose === true` marks final values.


### 3.2 Signals: Canonical vs Activity (Preview / Final / Whipsaw)

We separate **canonical signals** from **activity/preview** signals.

- **Canonical signals (ledger)**:
  - Paths (unchanged):
    - `pairs-data/{PAIR}/signals/{YYYY}/opens/{signalId}`.
    - `pairs-data/{PAIR}/signals/{YYYY}/closes/{signalId}`.
  - Extended contract:
    - `interval: 'DAILY' | 'WEEKLY' | 'MONTHLY'` (enum in code).
  - Creation rules:
    - Daily: from finalized daily RS (today’s POST).
    - Weekly/Monthly: **only** from RS samples where `isIntervalClose === true`.

- **Signals Activity / Whipsaw (new name)**:
  - Per-pair:
    - `pairs-data/{PAIR}/signals-activity/{YYYY}/days/{YYYY-MM-DD}`.
  - Root:
    - `signals-activity/{YYYY}/days/{YYYY-MM-DD}`.
  - Shape (conceptual):
    - `SignalsActivityDoc { date, events: ActivityEvent[] }` with:
      - `kind: ActivityEventKind` — enum: `OPEN | HOLD | CLOSE`.
      - `interval: Interval` — enum: `DAILY | WEEKLY | MONTHLY`.
      - `direction: RsDirection` — enum: `LONG | SHORT`.
      - `rsRaw`, `rsNorm` (normalized to [0,1]).
      - `state: ActivityEventState` — enum: `PREVIEW | FINAL | ABANDONED`.
      - `signalId?`.
  - Behavior per POST run (backfill or realtime):
    - Use the canonical `RsWriteEvent[]` produced by `runCanonicalRsEngineForPair` as the source of truth for which positions exist and when they open/close at each interval.
    - Call the shared helper `generateActivityFromWrites` to:
      - Group writes by `(interval, positionId)`.
      - Derive `openDay`/`closeDay` for each position.
      - Walk RS archive samples between those days and emit:
        - `OPEN` on the open day.
        - `HOLD` on intermediate days where the interval has a sample.
        - `CLOSE` on the close day (if the position is closed).
    - All emitted events are initially `state: PREVIEW`. Later workflows may:
      - Promote matching events to `state: FINAL` and attach `signalId` when linked to canonical `opens`/`closes`.
      - Optionally mark never-printed previews as `ABANDONED` for whipsaw analysis.


### 3.3 Positions (All Intervals Dynamic)

- `BePositionDoc` will gain an `interval` field of type `Interval` (enum: `DAILY | WEEKLY | MONTHLY`).
- Open positions at **all intervals** are updated on every run:
  - Append `PriceDatum` updates (`role: update`, `source: pre`) using the interval-appropriate RS + price.
- When the interval bar is finalized **and** a CLOSE signal prints:
  - Write an `exit` `PriceDatum` with `source: post`.
  - Set `netPnL` / `netPercentReturn`.
  - Move the position doc from `open` to the `{YYYY}-closed` shard.

This keeps positions **live** for dashboards while preserving canonical truth at interval boundaries.

## 4. Transition Phases

### Phase 0 – Planning Only (this doc)

- Document the target model (this file).
- Tag existing planning docs that still assume `signals-daily` or `pairs-data.data[]` with a “transition in progress” note.
- Add a task in `docs/tasks/PROTOTYPE.md` to complete the transition once implementation is done.

### Phase 1 – Backend Types & Constants (no behavior change)

- Introduce interval/enum types in functions code (without changing logic yet):
  - `Interval` enum for RS/Signals/Positions (`DAILY | WEEKLY | MONTHLY`).
  - Activity-related enums: `ActivityEventKind`, `ActivityEventState`.
- Add collection/constant names for `signals-activity` (per-pair + root) and any `latestWeekly` / `latestMonthly` accessors.
- Ensure existing daily behavior compiles unchanged.

### Phase 2 – Writer & RS Engine Enhancements (multi-interval data only)

- Extend the RS writer to:
  - Fetch **Weekly** and **Monthly** bars from AV/Savant alongside Daily.
  - Populate `latestWeekly` / `latestMonthly` and `archive-weekly-*` / `archive-monthly-*` according to this plan.
- Keep signals/positions **daily-only** for now.
- Validate:
  - Firestore shows D/W/M archives for a few test pairs.
  - No FE breakage (FE still only uses daily).

### Phase 3 – Signals Activity (Preview Layer)

- Implement `SignalsActivityDoc` and `ActivityEvent` in the functions code.
- On every run, for each pair and interval:
  - Use the RS engine on **current** RS series to compute preview events answering:
    - “If this interval closed right now, which positions would OPEN, which would remain HOLD, and which would CLOSE?”
  - Write/update `signals-activity` docs with these `ActivityEvent` entries using `state: PREVIEW`.
- Do **not** yet alter canonical signals/positions.
- FE experiments (optional):
  - Build a simple internal view that reads `signals-activity` and shows live previews per interval.

### Phase 4 – Canonical Multi-Interval Signals & Positions

- Wire weekly/monthly canonical signals:
  - When `isIntervalClose === true` for W/M and the RS engine emits events:
    - Write canonical `BeOpenSignalDoc` / `BeCloseSignalDoc` with `interval` set.
    - Update matching `ActivityEvent` entries to `state: FINAL`.
- Extend positions:
  - Add `interval` field to `BePositionDoc` and associated writers.
  - Ensure open positions for all intervals receive `PriceDatum` updates on each run.
  - Canonical CLOSE at interval boundaries as described.

### Phase 5 – Frontend Integration (Interval Toggle)

- Add an **interval toggle** to the RS dashboard / chart UI:
  - Options: `Daily`, `Weekly`, `Monthly`.
  - Drives:
    - Which RS series to load (daily vs weekly vs monthly archives).
    - Which set of `ActivityEvent`s to show by default.
- For each interval selection:
  - Charts:
    - Use the appropriate archive (`archive-*`) and `latest*` mirror.
  - Signals/Activity panel:
    - Query `signals-activity` filtered by `interval` and `state`.
  - Positions:
    - Filter positions by `interval`.

### Phase 6 – Cleanup & Doc Alignment

- After behavior is stable and FE uses the new capabilities:
  - Update all planning docs that still:
    - Reference `signals-daily` instead of `signals-activity`.
    - Assume `pairs-data.data[]` instead of archives + `latest*`.
  - Remove any deprecated references from README / older design notes.
